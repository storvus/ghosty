🧱 Living sandbox — требования
1. Идентичность и доступ
   Пользователь получает стабильный UID при первом входе
   Повторный вход по UID без полноценной авторизации
   Любой UID считается валидным (нет строгой аутентификации)
   Нет сессий в классическом смысле безопасности — только “привязка подключения к UID”
2. Подключение и транспорт
   WebSocket используется для всех realtime-событий
   WebSocket может быть активен всегда, пока клиент запущен
   Один UID может иметь несколько одновременных соединений (multi-device моделирование)
   Разрыв соединения автоматически переводит соответствующий session в “offline”
3. Bootstrap (обязательный REST слой)

При старте клиента всегда выполняется REST-запрос (или набор запросов), который даёт полную картину мира:

полный список всех пользователей системы
текущие presence-статусы всех пользователей
базовые данные для отображения UI

Это единственный источник “initial truth”.

4. Presence система
   Пользователь может менять свой статус (online / away / dnd / offline)
   OFFLINE выставляется автоматически при disconnect
   Presence обновляется realtime через WebSocket события
   Нет сложных правил приватности (invisible, exceptions отключены)
5. Сообщения
   Пользователь может отправлять сообщения любому пользователю
   Сообщения доставляются через WebSocket, если получатель онлайн
   Сообщения НЕ сохраняются на сервере
   Нет истории сообщений
   Нет гарантированной доставки (best effort)
6. Контакты / социальный граф
   Все пользователи считаются “контактами” друг для друга
   Нет добавления/удаления друзей
   Нет графа подписок
   Нет приватных списков
7. Realtime синхронизация (WebSocket события)

WebSocket используется только для:

presence updates
incoming messages
system sync events (например, user connected/disconnected)

WebSocket НЕ используется для:

initial загрузки состояния
критичных бизнес-операций с гарантиями
8. REST роль

REST используется только для:

bootstrap (полная загрузка состояния)
базовых операций регистрации UID

REST НЕ используется для realtime обновлений.

9. Согласованность и дубли
   Клиент обязан быть устойчив к дубликатам событий
   Все обновления являются “last write wins”
   Нет гарантии порядка доставки WebSocket событий
   При рассинхронизации клиент восстанавливает состояние через REST bootstrap
10. Хранение данных
    Минимальное persistent storage:
    user registry (UID → user)
    Presence и сообщения — in-memory (или ephemeral)
    🧠 Инвариант системы
    REST = полная картина мира
    WebSocket = непрерывные изменения этой картины
    ⚡ Главная характеристика sandbox

Система допускает:

потерю сообщений
дубли событий
отсутствие истории
временные рассинхронизации

но НЕ допускает:

невозможность восстановить текущее состояние через REST
