# Ghosty Message Model

Пользователь может отправить сообщение в DM (1:1). Формат:
```json
{
    "type": "message", 
    "client_message_id": uuid(),
    "recipient_ids": list[int] | null,
    "conversation_id": int | null,
    "content": "abc-123",
}
```
Когда письмо приходит на сервер, тот проверяет:
-1. проверка дубликата по client_message_id. Если это так, сервер возвращает ACK с существующим conversation_id и message_id:
```json
{
    "type": "message_ack",
    "client_message_id": "abc-123",
    "conversation_id": 999,
    "message_id": 5001
}
```
0. recipient_ids и conversation_id не могут быть одновременно заполнены, но и не могут быть одновременно пусты. Если это так, сервер возвращает ошибку:
```json
{
    "type": "message_error",
    "client_message_id": "abc-123",
    "error_code": "invalid_message_format"
}
```
1. Если conversation_id существует, сервер проверяет, разрешено ли пользователю писать туда:
   a. Пользователь принадлежит к этому conversation_id
   b. Пользователь не заблокирован в этом conversation_id
2. Если пришел несуществующий conversation_id???
```json
{
    "type": "message_error",
    "client_message_id": "abc-123",
    "error_code": "conversation_not_found"
}
```
3. Если conversation_id пришел пустым, сервер проверяет, есть ли уже существующий conversation_id для этого пользователя и получателя (использует conversation_key):
   a. Если есть, сервер связывает это сообщение с этим conversation_id.
   b. Если нет, сервер проверяет не заблокирован ли пользователь со стороны собеседника или не заблокировал ли он собеседника. Если нет, сервер:
    a. Создает новый conversation_key для этой пары пользователей.
   c. Создает новый conversation_id в БД и связывает его с обоими пользователями.
3. Сохраняет сообщение в БД
4. Отправляет ACK отправителю, подтверждая, что сообщение получено и сохранено, с указанием conversation_id и message_id.
```json
{
    "type": "message_ack",
    "client_message_id": "abc-123",
    "conversation_id": 999,
    "message_id": 5001
}
```
4.1. Если ответ собеседника придет раньше, чем ACK, клиент может не знать, к какому conversation_id привязать это сообщение (тут продумать, что происходит при переподключении). 
    кладем его в буффер и ждем ACK. Когда придет ACK, мы узнаем conversation_id и сможем применить buffered-сообщение к этому conversation_id. При перезагрузке кажется, не нужно хранить
    pending chats (?), так как на этот момент чат уже создан и придет при переподключении


4.2. (not for MVP) Без ACK-сообщения клиент попробует переслать его несколько раз, а затем выдаст ошибку пользователю. С ACK-сообщением клиент может быть уверен, что сообщение сохранено и не будет пытаться отправить его повторно.
5. Если произошла ошибка (например, пользователь заблокирован), сервер отправляет ошибку отправителю:
```json
{
    "type": "message_error",
    "client_message_id": "abc-123",
    "error_code": "user_blocked"
}
```
6. В случае ошибки сервер также оповещает клиента об этом, чтобы тот мог попытаться еще раз или пометить сообщение как неотправленное.
7. После отправки ACK, отправляет сообщение получателю, если он онлайн в формате
```json
{
    "type": "new_message",
    "conversation_id": 999,
    "message_id": 5001,
    "sender_id": 1,
    "content": "Привет!"
}
```
7.1. Если получатель офлайн, сервер сохраняет сообщение и доставляет его при следующем подключении получателя.
8. (not for MVP) Пользователь может создавать группы (групповые чаты) с несколькими участниками. Об этом в следующем разделе.
9. Клиент может подгружать историю сообщений, отправив GET-запрос к /messages?conversation_id=999&before_id=5000. Сервер возвращает список сообщений в этом conversation_id с message_id < 5000.
10. При пере/подключении клиент может отправить GET-запрос к /chats, чтобы получить список всех conversation_id, в которых он участвует, и последних сообщений в каждом из них. Это позволяет клиенту отобразить список чатов и последние сообщения при загрузке.
```json
[
    {
        "conversation_id": 999,
        "last_message_id": 5001,
    },
    ...
]
```

2. Ждём "connected" от сервера
3. Начинаем буферизовать WS события
4. GET /chats
5. Применяем chats к состоянию
6. initialized = true
7. Сбрасываем буфер по порядку
8. Показываем UI

         (пользователь открыл чат)

9. GET /messages?before_id=X
10. WS события с id > X уже идут — коллизий нет


## Out of MVP scope 
- Групповые чаты (группы с несколькими участниками)
- Редактирование и удаление сообщений
- Реакции на сообщения
- Read receipts ("прочитано")
- Push-уведомления
- Typing indicators ("печатает")
- Онлайн-статус пользователей
- Повторная отправка сообщений при потере соединения
- event-log (может быть, позже)
- media/files
- ✓ Refresh токены       → пока один долгоживущий (30 дней)
  ✓ OAuth / соцсети      → пока только логин/пароль
  ✓ Email подтверждение  → пока без него
  ✓ Rate limiting        → пока без него

event log (может быть, позже)
new_message          — новое сообщение (полный payload)
message_edited       — изменено сообщение
message_deleted      — удалено
message_ack          — твой ack при переподключении
messages_read        — собеседник прочитал до message_id=X
chat_created         — создан новый чат
chat_member_added    — добавился участник
chat_member_removed  — вышел участник
user_typing          — печатает (обычно не хранится!)
