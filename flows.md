# Стандартный флоу подключения к онлайн-сервису через вебсокет
1. Пользователь запускает клиентское приложение (далее Клиент)
2. Клиент проверяет наличие токена авторизации (далее Токен) в локальном хранилище. 
   1. Если Токен отсутствует, клиент перенаправляет пользователя на страницу регистрации/авторизации
3. Клиент устанавливает соединение с сервером (далее Сервер) через WebSocket и отправляет Токен для проверки. (Вопрос: нужно ли отправлять Токен при каждом сообщение по вебсокету или только при подключении?)
   1. Нужно ли ждать connected от сервера?
4. Сервер проверяет Токен:
   1. Если Токен действителен, сервер устанавливает коннект с Клиентом и разрешает дальнейшую работу.
   2. Если Токен недействителен, сервер отправляет ошибку и закрывает соединение. Клиент перенаправляет пользователя на страницу регистрации/авторизации.
   3. Если access_token близок к истечению → сначала refresh
5. Клиент начинает "буфферизацию" сообщений от сервера по вебсокету. 
6. Клиент отправляет API запрос на получение списка чатов и последних сообщений в каждом из них. 
   1. Сервер возвращает список всех conversation_id, в которых участвует пользователь, и последних сообщений в каждом из них. (Вопрос: какой формат ответа?)
7. Клиент отображает список чатов и последних сообщений в пользовательском интерфейсе.
   1. Как получить текст последнего сообщения? Отдельным запросом или в ответе на GET /chats? (Вопрос: нужно ли возвращать текст последнего сообщения в ответе на GET /chats?)
   2. Как клиент узнает, что есть непрочитанные сообщения в чате? Где-то на клиенте хранится информация о том, какие сообщения были прочитаны, а какие нет?
   3. Хранит ли сервер информацию о том, были ли сообщения ДОСТАВЛЕНЫ пользователю или нет? (например, если пользователь был оффлайн и не получил сообщение, сервер может пометить его как непрочитанное)
   4. Хранит ли сервер информацию о том, были ли сообщения ПРОЧИТАНЫ адресатом или нет?
8. Если пользователь кликает на чат, клиент переходит в "Процесс общения между пользователями" для выбранного conversation_id.

# Процесс поиска и добавления новых контактов
1. Пользователь нажимает кнопку "Find / Add Users"
2. Всплывающее окно открывается, и пользователь вводит username или display_number пользователя, которого он хочет найти.
3. Пользователь нажимает кнопку "Search"
4. Клиент отправляет API запрос на сервер для поиска пользователя по введенному username или display_number.
5. Сервер возвращает список пользователей, соответствующих критериям поиска:
   1. Полное совпадение по display_number
   2. Полное совпадение по username, неполное совпадение по username (например, поиск по подстроке) с сортировкой по релевантности:
      1. Точное совпадение display_number
      2. Точное совпадение username
      3. Starts with
      4. Contains
6. Клиент отображает результаты поиска в том же всплывающем окне.
   1. Напротив каждого найденного пользователя отображается кнопка "Message"
   2. Если это сам текущий пользователь, фильтруем его из результатов поиска.
7. Если пользователь нажимает кнопку "Message", клиент открывает чат с выбранным пользователем. 
   1. Если чат между выбранным адресатов и текущим пользователем уже существует на клиенте, клиент открывает существующий чат.
    ```js
    const existing = chats.find(c =>
        c.type === 'direct' &&
        c.participant_ids.includes(selectedUserId)
    )
    
    if (existing) {
        openChat(existing.conversation_id)
    } else {
        openPendingChat(selectedUserId)
    }
    ```
   2. Информация о собеседнике (username/display_number) сохраняется в кеше клиента, чтобы при открытии чата не нужно было делать дополнительный запрос на сервер.
   ```typescript
    // При нажатии "Message":
    setUserCache(prev => ({ ...prev, [user.id]: user }))
    ```
8. Если чат с этим пользователем не существует, клиент открывает новый чат
   1. Чат получает временный conversation_id только в момент отправки первого сообщения.
      1. использовать строковый ключ вместо числа "pending:<recepient_id>" vs "chat:<conversation_id>" - никаких коллизий


# Процесс общения между пользователями
1. Пользователь открывает чат с другим пользователем через список чатов или через поиск.
2. Если это новый чат, инициированный через поиск
   1. Чат пока не имеет conversation_id, клиент отображает временный чат с собеседником и позволяет пользователю отправлять сообщения.
   2. Чат не отображается в списке чатов до тех пор, пока не будет получен ответ от сервера с новым conversation_id.
   3. Чат соответственно не подсвечивается в списке чатов до тех пор, пока не будет получен ответ от сервера с новым conversation_id.
3. Если это существующий чат
   1. Чат подсвечивается в списке чатов.
4. В окне диалога пользователь видит username/display_number собеседника сверху по центру.
5. Пользователь может отправить текстовое сообщение.
6. Клиент отправляет сообщение на сервер через вебсокет. Формат сообщения:
    ```json
    // Существующий чат:
    {
      "type": "message",
      "conversation_id": 999,
      "client_message_id": "abc-123",
      "text": "Привет!"
    }
    
    // Новый чат:
    {
      "type": "message",
      "conversation_id": null,
      "recipient_id": 42,
      "client_message_id": "abc-123",
      "text": "Привет!"
    }
    ```
7. Клиент проверяет, существует ли чат на клиенте с указанным conversation_id. 
   1. Если чат существует, сообщение сохраняется в локальном буфере сообщений этого чата с флагом "pending" и отображается в окне диалога.
   2. Если чат не существует, клиент создает временный чат с указанным собеседником (по recepient_id или client_conversation_id), сохраняет сообщение в локальном буфере сообщений с флагом "pending" и отображает его в окне диалога.
8. Клиент сохраняет сообщение в локальном буфере сообщений с флагом "pending" и отображает его в окне диалога.
9. Сервер проверяет, что:
   1. Если conversation_id указан
      1. Такой чат существует
      2. Пользователь является участником чата
      3. Пользователь не заблокирован в чате
      4. client_message_id уникален для этого чата
          1. Если client_message_id существует, считается, что это повторная отправка сообщения и сервер не сохраняет сообщение.
          2. Как проверять существование? constraint violation:
    ```python

        await self.message_repo.create(...)
    except UniqueConstraintViolation:
        # дубликат - возвращаем существующий ack
        existing = await self.message_repo.get_by_client_message_id(
            sender_id, client_message_id
        )
        return existing
    ```          
   2. Если conversation_id не указан, указан ли recepient_id
       1. recepient_id существует и является действительным пользователем
       1. Пользователь не заблокирован у собеседника
       2. client_message_id уникален для этого пользователя
           1. Если client_message_id существует, считается, что это ошибка? Вопрос: Что делать?
       3. между пользователем и собеседником не существует другого direct чата
          1. сервер ищет по `conversation_key = sorted(sender_id, recipient_id)`.
          2. Если чат уже существует, сервер испльзует существующий conversation_id и игнорирует recepient_id
   3. Если не указан ни conversation_id, ни recepient_id, сервер игнорирует сообщение.
   
10. Если все проверки пройдены, сервер сохраняет сообщение в базе данных.
11. Сервер отправляет сообщение обратно клиенту с подтверждением сохранения. Формат ответа:
    ```json
    {
        "type": "message_ack",
        "conversation_id": number,

        "message_id": number, // айди сообщения в базе данных
    ```

12. Если остальные участники чата онлайн, сервер отправляет сообщение через вебсокет. Формат сообщения:

    2. Если чат не существует, клиент проверяет, существует ли временный чат с указанным собеседником (по recepient_id или client_conversation_id).

**Вопрос: Когда происходит сортировка сообщений на клиенте - при каждом новом сообщение сортировка по message_id DESC?**

Не обязательно сортировать весь массив - достаточно вставить в правильное место:
Pending сообщения всегда в конце
```typescript
// Два отдельных массива:
const confirmed: Message[] = []  // отсортированы по message_id, не меняются
const pending: Message[] = []    // в конце, в порядке отправки
// Рендерим:
const allMessages = [...confirmed, ...pending]
```
При получении ack:
```typescript
// Убираем из pending
const idx = pending.findIndex(m => m.client_message_id === ack.client_message_id)
pending.splice(idx, 1)

// Вставляем в confirmed - бинарным поиском по message_id
const insertAt = binarySearch(confirmed, ack.message_id)
confirmed.splice(insertAt, 0, { ...msg, message_id: ack.message_id })
```
При получении чужого сообщения через WS:
```typescript
// Чужие сообщения всегда confirmed, просто добавляем в конец
// message_id монотонно растёт → новые всегда больше
confirmed.push(newMessage)
```
Почему не сортировать весь массив
sort() на 1000 сообщений при каждом новом = O(n log n) каждый раз
бинарный поиск + splice = O(log n) + O(n) для вставки

Разница ощутима при активном чате
Для MVP честно - можно и sort() каждый раз, не заметишь на малых объёмах. Но два массива концептуально чище - pending и confirmed это разные состояния, разделение явное.

### Пропущено — before_message_id обновляется в двух местах
```
1. GET /chats  → oldestLoadedId = last_message_id (начальное значение)
2. GET /history → oldestLoadedId = min(message_id) из ответа
```

### Пропущено — hasMore флаг
```
history.length === limit → hasMore = true
history.length < limit  → hasMore = false, IntersectionObserver не триггерит
```

### Пропущено — out-of-order ack и прыжки сообщений
Pending сообщения не переносятся в confirmed по одному — только подряд с начала:
```typescript
while (pending[0]?.status === 'confirmed') {
    insertSorted(confirmed, pending.shift())
}
```

### Пропущено — обновление last_message
```
1. Сами отправили  → optimistic update сразу (клиентское время)
2. Получили WS     → обновляем после получения (серверное время)
3. После ack       → уточняем created_at серверным временем
```

### Пропущено — наполнение userCache
```
1. GET /chats        → participants всех чатов
2. GET /users/search → результаты поиска
3. WS new_message    → sender объект в событии (если нет в кэше)
```

### Пропущено — presence
```
GET /chats          → is_online для каждого участника (снимок)
WS presence событие → обновляем userCache в реальном времени
```

### Reconnect
