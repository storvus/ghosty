# 🧱 Финальная система (single-node, без шардинга)

Это целевая архитектура полноценного realtime-мессенджера на одной машине.  
Не sandbox, а уже “нормальная” система с устойчивой моделью данных и realtime-слоем.

---

# 1. Идентичность и доступ

- У каждого пользователя есть стабильный `UserId`
- Пользователь аутентифицируется через токен (упрощённый или базовый)
- Поддерживается повторный вход по тому же `UserId`
- Один пользователь может иметь несколько активных сессий (multi-device)

---

# 2. Модель сессий

- Сессия = WebSocket соединение + серверное состояние
- Каждое соединение привязано к `UserId`
- Сессии независимы друг от друга
- При разрыве соединения удаляется только сессия, не пользователь
- Пользователь считается “онлайн”, если есть хотя бы одна активная сессия

---

# 3. ConnectionManager (runtime слой)

- Хранит все активные WebSocket соединения в памяти процесса
- Умеет:
    - отправить сообщение конкретному пользователю
    - отправить группе пользователей
    - сделать broadcast
- Не хранит бизнес-состояние
- Не знает ничего о БД

---

# 4. Bootstrap (REST слой восстановления состояния)

При подключении клиента всегда выполняется REST-запрос, который даёт полную картину состояния:

- список пользователей (или друзей)
- текущие presence статусы
- социальный граф (друзья)
- настройки visibility
- начальное состояние интерфейса

Это единственный источник полной “истины мира” для клиента.

---

# 5. Presence система (центральная realtime логика)

## Статусы:
- online
- away
- do_not_disturb
- invisible
- offline (вычисляемый)

---

## Правила:

- Presence хранится как текущее состояние, не как лог событий
- Изменения presence распространяются через WebSocket
- OFFLINE выставляется автоматически при отсутствии всех сессий
- Invisible влияет только на видимость, но не на факт активности

---

## Видимость:

- Пользователь может скрывать свой presence глобально
- Может иметь список исключений (visibility exceptions)
- Сервер всегда вычисляет “эффективный presence”
- Клиенты никогда не получают внутренние правила видимости других пользователей

---

## Рассылка presence:

- Рассылается только тем пользователям, которым разрешено видеть статус
- В WS отправляется только итоговое состояние (не правила)

---

# 6. Социальный граф (друзья)

- Пользователь может добавлять и удалять друзей
- Граф хранится в БД
- Изменения графа синхронизируются через WebSocket
- Используется для:
    - фильтрации presence
    - определения аудитории сообщений

---

# 7. Сообщения

- Пользователь может отправлять сообщения другим пользователям
- Сообщения доставляются через WebSocket (если возможно)
- Сообщения обязательно сохраняются в БД
- Есть уникальный `message_id`
- История сообщений доступна через REST

---

# 8. Семантика доставки сообщений

- доставка “как минимум один раз” (at-least-once)
- клиент обязан уметь дедуплицировать сообщения
- порядок сообщений гарантируется только частично (best-effort)

---

# 9. WebSocket слой

WebSocket используется для:

- доставки сообщений
- presence updates
- обновления друзей
- системных уведомлений
- typing событий (опционально)

WebSocket НЕ используется для:
- получения полного состояния
- критических операций с гарантиями доставки

---

# 10. REST API

REST отвечает за:

- аутентификацию
- bootstrap (полное состояние)
- изменения друзей
- изменения visibility настроек
- получение истории сообщений

---

# 11. Модель консистентности

- система допускает eventual consistency
- события могут приходить с задержкой или повторяться
- клиент всегда может восстановить состояние через REST
- WS события — это ускорение, а не источник истины

---

# 12. Синхронизация состояния

При подключении или переподключении клиент:

1. делает REST bootstrap
2. получает полное состояние
3. подключается к WebSocket
4. получает только дельты после этого момента

---

# 13. Хранение данных

## В базе данных:
- пользователи
- друзья (социальный граф)
- настройки visibility
- сообщения

## В памяти процесса:
- активные WebSocket соединения
- карта user_id → sessions
- кеш presence

---

# 14. Обработка ошибок и потерь

- потерянные WS события допустимы
- дубликаты событий допустимы
- клиент всегда может восстановиться через REST
- reconnect всегда приводит к полной ресинхронизации

---

# 15. Идемпотентность

- все WS события должны быть идемпотентны
- клиент должен использовать last-write-wins модель
- состояние пересобирается из последних известных данных

---

# 16. Жизненный цикл соединения

1. подключение WebSocket
2. идентификация пользователя
3. bootstrap через REST
4. переход в активное состояние
5. realtime поток событий через WS
6. disconnect → очистка сессии
7. reconnect → повторный bootstrap

---
